# @stet-css/lexer

Owns **lexical scanning** with exact source ranges: class-list parsing and tokenizing, JavaScript string and template body decoding (`decodeStetCSSScriptString`, the `scriptString` class-list option) that maps decoded classes back onto their source spelling, HTML attribute value and JSX attribute string character-reference decoding (`decodeStetCSSHTMLAttributeValue`, `decodeStetCSSJSXAttributeString`, exported from `@stet-css/lexer/character-reference` only) with the same source mapping, which class-list parsing takes as its `characterReferences` option (alone, or before `scriptString` for a string inside an attribute; `decodeStetCSSClassListSource` gives the combined decode), CSS directive ranges, `@import` statement scanning for manifest entries, CSS value and variable-reference helpers, the JS/TS nesting-depth prescan, and unit constants. It returns tokens and ranges; consumers validate and compile them.

## Boundaries

- Class lists vs candidates: lexer parses a class list it is handed (`parseStetCSSClassList`); finding class-like strings in arbitrary source is `@stet-css/source`.
- Directives and entries: lexer locates directive ranges and entry statements; `@stet-css/compiler` parses and lowers directives, and `@stet-css/project` decides which files are entries.

## Risks

- **Source ranges** hold across tokenization boundaries, duplicate tokens, escaped quote and backtick tokens, and cursor or empty positions (`includeEmpty`). `@stet-css/language`, `@stet-css/lint`, and `@stet-css/eslint-plugin` map diagnostics and edits through them; when a range fix changes what a consumer receives, cover it in that consumer's tests too.
- **Runtime class fragments** (`getStetCSSWholeClassRange`, `getStetCSSTemplateExpressionNeighbours`): `@stet-css/language` and `@stet-css/eslint-plugin` both decide through them which text beside a runtime expression is a fragment, so a change moves editor positions and ESLint reports and fixes together.
- **Import and directive scanning** feeds compiler parsing, project entry discovery, and editor tokens, so a scanning change reaches all three.
- **CSS escape, string and comment skip** (`skipCSSEscapeStringOrComment`): besides this package's directive, import and value scanners, `@stet-css/compiler` skips through it in its directive, value and import-condition scans and in its selector alias scan, every selector list split goes through `splitCSSSelectorList` (compiler nesting and wrappers, `@stet-css/stylesheet`'s scoped Vue `:global()` wrapping), and `@stet-css/language` in its CSS semantic tokens. A change to what it skips changes compiler CSS output. `replaceCSSNestingSelector` skips through it too, and every `&` nesting replacement in `@stet-css/compiler` and `@stet-css/engine` goes through it, so a change there also changes runtime CSS output in the browser.
- **Script nesting prescan** (`exceedsScriptNestingLimit`) gates oxc parsing inside the `oxc-stack.ts` module that `@stet-css/source` and `@stet-css/language` each keep: oxc-parser overflows its native stack on deep nesting and kills the process. Counting a construct short lets a crashing file through; counting it long sends ordinary files to text extraction or regex scanning, which find different classes. Its docstring lists what it counts short on purpose (chains split across lines, closing brackets inside strings, comments or regular expressions). Sources up to 1 KiB parse inline on the caller's stack, as small as a default 4 MB worker-thread stack; longer ones parse on a stack sized to the source, at 1 KiB per character, which assumes the limit caps bracket nesting (brackets cost oxc up to ten times more stack per character than uncounted chains). The `deep-nesting` tests guard both: source feeds the deepest input of 1 KiB or less in every shape to a default-stack worker, source and language feed the deepest input the prescan allows (over 1 KiB, so it parses on the sized stack), and language feeds 128 KiB of dense brackets that the sized stack cannot carry without the prescan. Rerun them after raising the limit or upgrading `oxc-parser`.
- **Character references**: `src/html-named-references.ts` holds the WHATWG named-reference list, which the standard keeps fixed, plus the XHTML subset JSX compilers decode. The HTML decoder follows the tokenizer's attribute-value rules, not `entities`/htmlparser2 or Svelte, which differ on legacy names before an alphanumeric and on multi-code-point values. The decoders stay off the root entry, which engine and so `@stet-css/runtime` import, so the browser bundle cannot pull the table in even without tree-shaking; the root's `characterReferences` option takes a decoder as a value for the same reason. `@stet-css/source` (the build), `@stet-css/language` (editor and lint class positions) and `@stet-css/eslint-plugin` all read class attributes through these decoders, so a decoding change moves extracted CSS, editor positions, lint reports and autofixes together.
- **Dependency-free**: `dependencies` stays empty unless the task explicitly justifies one.
